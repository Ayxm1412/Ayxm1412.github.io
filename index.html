DeepSeek Harness / Cordis 架构解析

发表于 2026-10-21 分类于 技术

0. 核心结论

  1. 一切皆插件：模型适配、工具、会话、沙箱，连 agent loop 本身，都是挂在同一个 ctx 上的插件；没有特权内核，均可从配置替换。
  2. Cordis 是微内核：内核只做四件事——服务解析、注册、事件 IPC、生命周期。插件=镜像，Fiber=进程，注册=可逆 effect，事件=IPC，能力接口=可热插拔的驱动（seam）。
  3. Session Log 是一等公民：整段对话是一条 append-only 的事件日志（event sourcing），是唯一事实源；模型看到的 Surface、人看的 Transcript、todo/goal 状态，都是从这条 log 派生的读模型。压缩只改投影，不改 log。
  4. Capability Seam = 稳定契约 + 可替换实现 + 明确消费者：更换 provider（本地↔沙箱↔远程）时，消费者代码无需修改。
  5. 代价：概念层叠、复杂度不消失只是转移、单进程不构成安全沙箱、provider 契约依赖约定而非强制。它面向”复杂、动态、可自进化”的 Agent 场景，并非通用解。
  6. 运行模型：单进程 + 单 JS 线程；多会话是 async/await 协程，在一个事件循环上交替（并发而非并行），真并行仅出现在模型请求与子进程；共享 JS 状态无需加锁，多会话修改同一文件依赖版本乐观锁（FS_STALE_VERSION）。
  7. 搜推 harness 与通用 harness 不同：通用 harness 面向”开放式、低 QPS、长程、模型驱动”优化，搜推面向”闭形状、高 QPS、短程、时延敏感、pipeline 驱动”优化。做法是借鉴 DSH 的 seam / 双轨 / 配置分层，不采用微内核热插拔与热路径上的模型循环（详见第 13 节）。

从 DeepSeek Harness 看 AI Native 软件的长期维护

发表于 2026-10-21 分类于 技术

最近，日常研发中的大部分实现已经交给了 Agent，也写了不少用完即弃的“日抛代码”。我尝试过 Spec 驱动开发，希望把需求和实现管得更清楚。但代码越积越多，遇到问题时，还是经常只能再向 Agent 求助。

相比亲手写的代码，这些产出少了一些掌控感。新需求来了，或者出了 Bug，又回到“描述愿望，等待结果”的循环。Agent 能把代码写出来，但怎样才能让它成为团队真正理解、能够持续维护的软件？

《AI Native 研发范式实践手册》也记录了类似的“消化障碍”：团队并行使用多个 Agent，产出变多了，沟通方案时却未必能讲清设计，还得重新问 Agent。[1] 个人产能提高，并不等于团队的理解、评审和接手能力同步提高。

正巧最近读了 DeepSeek Harness 的部分源码。它以 Cordis 插件组织模型请求、工具执行和会话记录，仓库还维护着开发约定、文档检查、回放测试和设计说明。这些不直接实现功能的文件，提供了一个观察软件长期维护的窗口。

下面从问题定义、架构、文档和验证几个方面展开，再讨论开发进一步提速后，工具和工程师的工作可能怎样变化。文章结合个人实践与源码观察，由 Agent 协助润色。
