DeepSeek Harness / Cordis 架构解析

发表于 2026-10-21 分类于 技术 阅读次数：

0. 核心结论

  1. 一切皆插件：模型适配、工具、会话、沙箱，连 agent loop 本身，都是挂在同一个 ctx 上的插件；没有特权内核，均可从配置替换。
  2. Cordis 是微内核：内核只做四件事——服务解析、注册、事件 IPC、生命周期。插件=镜像，Fiber=进程，注册=可逆 effect，事件=IPC，能力接口=可热插拔的驱动（seam）。
  3. Session Log 是一等公民：整段对话是一条 append-only 的事件日志（event sourcing），是唯一事实源；模型看到的 Surface、人看的 Transcript、todo/goal 状态，都是从这条 log 派生的读模型。压缩只改投影，不改 log。
  4. Capability Seam = 稳定契约 + 可替换实现 + 明确消费者：更换 provider（本地↔沙箱↔远程）时，消费者代码无需修改。
  5. 代价：概念层叠、复杂度不消失只是转移、单进程不构成安全沙箱、provider 契约依赖约定而非强制。它面向”复杂、动态、可自进化”的 Agent 场景，并非通用解。
  6. 运行模型：单进程 + 单 JS 线程；多会话是 async/await 协程，在一个事件循环上交替（并发而非并行），真并行仅出现在模型请求与子进程；共享 JS 状态无需加锁，多会话修改同一文件依赖版本乐观锁（FS_STALE_VERSION）。
  7. 搜推 harness 与通用 harness 不同：通用 harness 面向”开放式、低 QPS、长程、模型驱动”优化，搜推面向”闭形状、高 QPS、短程、时延敏感、pipeline 驱动”优化。做法是借鉴 DSH 的 seam / 双轨 / 配置分层，不采用微内核热插拔与热路径上的模型循环（详见第 13 节）。

以下各节均从待解决的问题出发。

1. 问题起点：Agent Loop 的持续膨胀

传统 harness 将各类逻辑集中于一个巨型 Agent Loop 内：读文件需调用工具，工具需先启动沙箱，执行前需权限校验，token 超限需压缩上下文。每新增一项功能即向 loop 内追加代码，loop 持续膨胀、可维护性下降。

DSH 的应对是微内核：将 loop 拆薄，能力下沉为插件；插件通过 service（获取能力）与 event（拦截/协作）与内核交互。

以操作系统类比：内核只提供机制（调度、IPC、命名、资源归属），策略位于用户态服务。DSH 中”agent loop 本身也是插件”是该原则的字面实现——不存在可被直接打补丁的特权核心，扩展只能以新增插件的方式进行（docs/architecture.md）。

2. 机制一：插件即进程

先区分两个概念：

  • Plugin = 可执行镜像：函数/类 + inject（依赖声明）+ Config + provide。
  • Fiber = 该镜像的一次运行实例，即进程：持有 uid（PID）、state、config、ctx（地址空间）、disposables（持有的资源）。

其生命周期对应一张进程状态图：

对照 OS：PENDING≈阻塞（等待依赖）、LOADING≈创建、ACTIVE≈运行、FAILED≈崩溃、UNLOADING≈退出、DISPOSED≈终止。需注意 PENDING 并非”线程被挂起”，而是声明式前置条件：依赖未就绪时回调不会被调用。

资源释放是该设计的核心（论文称为”时间可组合性”）：每个注册都是一个可逆 effect，卸载时按逆序执行 disposer，类似 Go 的 defer 与 C++ 析构函数：

因此编写插件时无需手写卸载逻辑：ctx.on(...)、ctx.provide(...)、ctx.effect(...) 均返回 disposer，fiber 卸载时统一回收，从而保证卸载后不残留副作用。

3. 机制二：通信即中间件

插件之间不直接调用，而是经由内核的事件总线（IPC）。五种派发模式对应五种通信语义：

模式 语义 OS / 中间件类比
emit 广播，不等返回 信号 / 数据报
parallel 扇出，等所有 scatter-gather
serial 有序，遇 bail 停 责任链
bail 同步有序，第一个非空胜出 解析器 / 权限查询
waterfall 拦截器链，next() 委托、不调用即否决 filter driver / LSM 钩子

waterfall 将”事件”从通知升级为流程控制：

DSH 的请求拦截、工具执行前后的审批 / 沙箱 / 护栏均挂载在这几个 waterfall 上（agent/request、tools/pre-execute 等），而 agent loop 对其存在无感知。

4. 机制三：状态即事件溯源

多数 Agent 将 Session 存储为 message list；DSH 采用不同方式——它是一条 append-only 的事件日志，是唯一事实源；模型历史由其派生，不单独存储。即软件工程中的 event sourcing。

需区分三个不属于同一层次的概念：

  • Session Log：持久、append-only 的事实源（event store）。
  • Event Bus：瞬时、进程内的 IPC。session/event 即把”日志追加了一条”广播出去。
  • Surface：从 log 派生的一个读模型——模型实际看到的那条投影。

每条产消息的事件带一个 surfaceOp：append（正常追加）或 replace（替换 surface 上的一段）。上下文压缩即一条 replace——它仅在 Surface 层将旧消息 shadow 掉，log 中的原始事件不被删除。因此模型看到的是摘要，而回放 / transcript 始终可获取全文。这即”双轨迹”设计，也对应 CQRS 的多读模型：不同 surface 均为同一数据源的投影。

另有一条硬约束：model-visible ⟺ logged——任何进入模型请求的内容都必须能从 log 重建。

5. 机制四：能力接缝（Capability Seam）

将 Seam 理解为”接口”只说对了一半。Seam 是由三个角色组成的完整能力边界：

  • Service Definition：拥有 ctx.<key> 与词汇类型的 Cordis Service（是抽象类，不是 TS interface），标准由它定义。
  • Provider：真正实现（如 ctx.fs 的 fs-local / fs-sandbox / fs-ssh）。
  • Consumer：通过 inject 该 key 使用（如 tool-fs）。

插件相互独立，其交互与调用决策通过两条内核中介的通道完成（service inject/provide、events），且读取 ctx.X 而未在 inject 中声明会直接抛错——即能力式访问控制（类似 seL4 的 capability）：

调用决策被拆分为四方：Consumer 决定要什么（依赖 key，不依赖具体实现）；内核决定使用哪个 provider（按 scope + 激活态解析）；Provider 决定如何实现；waterfall 监听器决定是否放行 / 改写（审批、沙箱即由此插入）。不存在插件之间的硬连线。

关于”标准集合”的来源：它不是手工维护的注册表，而由 scripts/gen-doc-graphs.ts 扫描 Cordis 声明自动生成 docs/capability-seams.md 汇总表。core 脊柱（sessions/tools/llm/agents）因被广泛 inject，成为事实上不可替代的标准。

6. 机制的实际运行：一次完整对话

示例：在 Web 端输入”修复 foo.ts 的 bug 并运行 pnpm test”。

整体链路：客户端 →(RPC)→ SessionController 恢复 Agent → AgentLoop 开启 turn、向 log append turn/start + user/message → 组装 prompt+tools、经 ctx.llm 流式请求（agent/assistant-stream 是瞬时的打字机流，不入 log）→ settled 后 append assistant/message（持久，内嵌流）→ 模型需调工具则 append tool/call、经 tools/* waterfall（审批 / 沙箱在此拦截）→ 经 ctx.fs / ctx.shell seam 执行 → append tool/result → 每次 append 均 emit session/event，推给持久化（异步写 JSONL）、投影、客户端渲染 → 直至 turn/end。

Desktop 与 Web 的机制完全一致，差异仅在载体：Electron 主进程启动 Host、运行同一套 Web 应用，通过 Node IPC 传递启动 / 就绪 / 关闭信号。

7. 插件热插拔

由于一切皆 effect 且依赖为声明式，插件可在运行时替换。provider 更换（产生新 uid）后，内核通知依赖它的 consumer；consumer 的 epoch（由依赖提供方 uid 组合成的指纹）随之变化，触发其自动卸载并重载：

这即论文所述的”空间可组合性”：依赖关系在运行时被持续维护，环境变化时待激活 / 待移除的插件由框架自动判定，无需手工编排启动顺序。HMR 修改文件、cordis.yml 修改配置均经由该路径生效。

8. 横向对比：一等公民的差异

LangGraph Deep Agents DSH / Cordis
一等公民 State 快照 State（继承 LG） Session Log 事件流
持久化 Checkpointer 存每步 state 快照，可 time-travel 同 LG；文件可进 state 被 checkpoint Event sourcing：log 是源，surface 派生
agent 是 用户定义的图（nodes + reducers） LG 图 + 深度 agent 配方 一个插件：fold log → 调模型 → append

概括：**LangGraph 属于”状态快照溯源”，DSH 属于”事件溯源”**。”session log 是一等公民、agent 仅是处理器”这一判断在 DSH 中近乎字面成立；在 LangGraph 中对应的表述是”state 是一等公民”。

一处值得注意的取舍：Deep Agents 的 StateBackend 将虚拟文件纳入 checkpoint，time-travel 可连同文件状态一起回滚；DSH 的 fs 是带副作用的 seam，log 中仅记录工具事件，重放不恢复外部磁盘状态——即”外部副作用无法消除”的固有问题。

9. 深入 ctx：被 Proxy 包装的服务容器

前文将 ctx 简述为”插件的工具箱”。本节对其展开分析——它是理解整套框架的关键。

ctx 的本质是一个被 JS Proxy 包装的 Context 对象。构造函数最终 return self（self 为 proxy），因此外部获得的 ctx 并非普通对象，而是每次属性读取都经过拦截处理的对象：

每个插件有自己的 ctx，但共享同一个 root。 空间关系：

  • root ctx 持有两样全局共享的资源：服务登记册（reflect.store：记录谁 provide 了什么）与事件总线（events）。
  • 每个插件的 ctx 由 root 派生（原型继承），各自持有一个 fiber；彼此隔离，但共享同一 root。
  • 因此插件间通信并非”挂载在某个 ctx 上”，两条路径均经过 root：服务（provide/inject，登记册中点对点）与事件（emit/on，总线广播）。

读取 ctx.llm 并非简单取字段，而是一次”服务解析”：拦截器在读取时查询提供方、激活态与调用资格：

静态字段无法满足这些需求：值会随热插拔过期、无法做 inject 授权、无法按作用域解析、无法被拦截。因此每次读取均即时解析（这也是其类似”系统调用”的原因：所有访问收敛到一个可施加统一策略的入口）。

ctx 上没有固定的字段清单。 仅少数内核自带成员（on/emit/effect/provide/inject/plugin/get/set，来自四个内核服务的 mixin）；其余 llm/tools/web/sessions/fs… 均由插件在运行时注入。IDE 中观察到 ctx”字段众多”是表象——它由上百个包通过声明合并拼接而成：

若未加载 dsh-web，则 ctx.web 不存在，读取时抛出 cannot get property "web" without inject。

多个插件提供同一 key 的处理：同一作用域内重名会在加载时抛错，不存在歧义解析。需要多种实现时，采用以下三条路径：

“消费者获得的引用一定有效”由反应式生命周期保证：未就绪不激活（停留 PENDING）、失效即抛错、provider 更换时消费者自动重载（见 §7）、拆除时等待依赖方 settle。框架保证结构性正确（唯一性/解析/生命周期），但不保证 provider 的语义正确——后者依赖契约与测试。

上述机制可对应若干经典设计模式：

现象 模式
ctx 被 Proxy 包着、读写被拦截 代理模式 (Proxy)
读 ctx.key 去全局表按名查服务 服务定位器 (Service Locator)
inject 声明依赖、框架等齐了才激活 依赖注入 / IoC 容器
ctx.on/emit 广播 观察者 (Observer) + 事件总线
waterfall 的 next() 链 责任链 (Chain of Responsibility)
ctx 把多子系统统一成一个入口 门面 (Facade)
effect/disposer 逆序释放 RAII / Disposable

严格而言 ctx.llm 属于 Service Locator（按 key 主动获取），而非纯 DI（由容器注入引用）；Cordis 兼具两者：声明与激活具有 DI 容器特征，取值具有 Locator 特征。

插件开发约束（详见 §5 与 cookbook）：先以 inject 声明依赖；优先注册进已有 seam；所有贡献包进 effect（自动回收）；不将服务引用缓存到激活周期之外；可调参数置于 Config 而非硬编码；waterfall 监听器必须调用 next()。

10. 运行模型：单进程单线程，多会话以协程方式交替

一个常见的直觉是”多个会话对应多个线程”，该直觉不成立。

整个 dsh 运行在一个 OS 进程、一个 JS 线程（事件循环）上。直接证据：packages/core（session / agent / agent-loop 所在）中不存在任何 worker_threads / new Worker。真实线程与进程仅出现在边缘（见下文）。

多会话的”同时”推进依赖 async/await 协程：

  • 一个会话的 turn 运行到 await（等待模型返回、子进程、文件 I/O）即让出线程，由另一个会话继续执行；模型的流返回后它再恢复。任意时刻只有一段 JS 在执行——因此是并发（交替），而非并行（同时）。
  • 类比：Python 的 asyncio，或去除多线程 runtime 的 Go goroutine（所有协程固定在一个 OS 线程上）。
  • 命名注意：Cordis 的 “Fiber” 不是协程，它是插件的生命周期对象（uid / state / disposables）；协程性来自插件代码中的 async/await。

真正的并行发生在 JS 线程之外：三个会话同时请求模型即三个 HTTP 请求并发在途（socket 由 libuv / OS 管理）；会话 A 与会话 B 各自执行 bash 即两个真实 OS 子进程在不同核上并行。JS 本身单线程，但其等待的外部操作是并行的。真实线程 / 进程仅存在于这些边缘：subprocess / terminal / ssh 启动的子进程、inspector 的 Worker、Electron 桌面的多进程壳。

单线程协作的主要收益：无需加锁。 共享的 JS 状态（session 表、注册表、投影缓存）不会被两段 JS 同时修改——因为不存在两段 JS 同时执行。代价是：任何同步阻塞的长循环（不 await）会阻塞进程内所有会话；因此重计算均交由 await（异步）或子进程承担。

冷会话与活会话不同：会话列表中”打开”100 个并不意味着 100 个活 Agent 占用线程。冷会话仅是磁盘上的 log（ctx.sessionController 的 inspect() / page() 可冷读而不激活 Agent）；仅在调用 prompt() / resolveAgent() 时才恢复一个活 Agent 进入线程。因此挂载大量历史会话不会造成阻塞。

两个会话同时修改同一文件

这是单线程无法解决的问题——文件系统是外部共享可变状态，位于 JS 线程控制之外。DSH 不加锁，而是在 ctx.fs seam 内采用乐观并发控制（即数据库领域的 optimistic lock）（docs/subsystems/filesystem.md）：

  • 每个文件持有一个版本令牌 FsVersion；
  • 每个会话各自记录其观察到的文件版本（WeakMap<owner = agent.session, …>，按会话隔离）；
  • 写 / 改默认带 replaceIfVersion 守卫，版本不匹配时报 FS_STALE_VERSION 并拒绝覆盖（而非静默 clobber）。

单个 write / edit 本身是原子的（不会出现半写文件）。若需完全避免冲突，则通过 seam 做物理隔离：每会话独立 working directory、sandbox 围栏（越界写报 FS_SANDBOX_DENIED）、fs-ssh 推送至远程、git worktree 各分配一个工作树——即更换 provider / 作用域，而非依赖线程。

小结：单线程保证”DSH 内部共享状态无需加锁”；外部文件系统这类共享可变状态，依赖”异步不阻塞 + 原子写 + 版本乐观锁 + 作用域隔离”，而非”一个修改、另一个等待”。

11. 局限与代价

  • 复杂度未消失，只是转移：概念层叠（Service/Effect/Seam/Surface/Bundle/Profile/Patch…），DSH 自身需依赖大量 verify-* gate 与文档预算才能维持可控。
  • 单进程，Scope 只是逻辑隔离，不是安全沙箱：所有 context 共享一个 JS 堆；真隔离需依赖 subprocess / sandbox / ssh seam 将执行推到进程外。
  • 一切皆事件 + Proxy 解析：热路径存在开销，栈追踪被 proxy 干扰，”跳定义”无法定位运行时真正绑定的实现。
  • 生命周期正确性极难：vendor/README.md 的二十多条本地修改中有多条用于修复 fiber 可重入释放的缺陷——上游框架自身亦曾遗漏。
  • core 亦为插件，任何插件均可修改，易产生耦合；provider 契约依赖约定，冲突在运行时才暴露。
  • 非通用协议：属于 Harness 内部私有定义，生态尚早期（不同于已跨厂商的 MCP）。

12. 延伸：代码全由模型编写时的问题演变

判断：**瓶颈从”编写代码的成本”转移为”信任代码的成本”**，上述局限可分为三类——

  • 可溶解（本质是人类认知与手写成本）：概念爆炸、抽象成本、事件图谱难查、语法契约。由于 Cordis 是机器可读的（typed key、声明式 inject、生成的目录、机械化 gate），重契约框架相比依赖隐性知识的框架更适配模型作为作者。
  • 不溶解甚至加剧（结构性 / 物理性）：单进程隔离（模型自主 mount 插件时更需要不可绕过的沙箱）、proxy / 事件的性能开销、语义正确性（类型≠行为）、涌现行为（N 个模型编写的 listener 挂在同一条 waterfall 上）。
  • 发生变形：冻结且加固的内核是热插拔的前提，但同时构成固定上限——模型能力再强也无法突破框架自身的表达力边界。

概括：将作者替换为更强的个体并不能解决信任 / 验证 / 隔离问题；作者变强只意味着代码产出速度快于验证速度——即前述熵增在新前提下由副作用升级为主要矛盾。

这一点与第 4 节相呼应：使”模型自主修改自身”可信的唯一途径是系统可重放、可审计——即那条 log。因此 “log 是一等公民”与”模型编写一切代码”是同一前提下的两个推论：当作者是无法完全验证的模型时，append-only、可重放的 log 是唯一的信任锚。

13. 借鉴 DSH 设计高 QPS 搜推 harness：差异分析与取舍

前 12 节讨论的是 DSH 这套通用 agent harness。将其应用于电商搜推这类在线高 QPS 场景时会发现，其中一部分设计是为另一类问题付出的成本。本节先厘清通用 harness 与搜推 harness 的差异（差异 → 原因 → 解法），再给出一个可落地的两层设计。

13.1 一个根因，七处差异

所有差异均源于同一组坐标轴上的定位不同：

坐标轴 通用 harness（DSH） 搜推 harness（在线）
QPS 人工交互量级：一个会话一次请求 千~万级 / 秒
时延预算 分钟级可接受 p99 几百 ms ~ 几秒，硬预算
单程时长 长：一个 session 运行较久 短：一次请求一次响应
下一步谁定 模型（ReAct / TAO 循环） 流程（召回→排序是已知形状）
状态 会话级、长存、需可重放 请求级无状态；多轮仅为一个小 surface
出错代价 不可逆动作（删文件、push） 只读操作：风险为结果质量、时延超预算与推理成本
组件空间 开放、持续变化 封闭、已知、部署期才变化

根因概括：DSH 面向”开放式、低 QPS、长程、正确性关键、模型驱动”优化；搜推面向”闭形状、高 QPS、短程、时延关键、pipeline 驱动”优化。 若按错误的问题类型选型，将承担不适配的全部成本。

七处差异及其原因与解法：

# 维度 通用 harness 搜推 harness 原因 解法
1 谁驱动循环 模型每步决策，loop 围绕不可预测的模型推进 ~95% 走固定 pipeline 编码任务的下一步取决于运行时读取到的内容，事先未知；搜索的下一步（检索流程）是已知形状。模型驱动循环提供的灵活性在该场景无收益，而引入的时延不可接受 快路径 = 固定 LangGraph DAG（编译一次、无循环）；模型只出现在有界点（重排/合成/意图）；开放式 query 才进入 agentic 循环
2 状态 Session Log 一等公民、append-only、长存 请求无状态；多轮 = Redis 中带 TTL 的小 surface DSH 的 log 使长时、高成本、难复现的运行可重放并可喂训练，其成本被低 QPS 摊薄；搜推场景每请求写全量 log 收益低，成本却随 QPS 放大（写放大） 双轨：Surface（小、同步、Redis、TTL）供模型与多轮；Trace（全、异步、Kafka/OTel）供观测与训练，离开热路径
3 时延模型 无硬预算，recursion_limit 仅作安全网 p99 硬预算 交互式人工等待与受 SLA 约束的在线流量对时延的要求不同 两层 gate + 硬上限（轮次/时延/token）+ 达到上限时降级（返回部分最优结果 + 继续入口）+ 缓存将计算移出热路径
4 智能在哪 单一大模型承担全部任务 模型金字塔 + 大量非模型算力 百万级商品排序是表示学习问题，小模型 + ANN 索引的成本比 LLM 逐条读取低数个量级；QPS 也禁止每请求调用大模型 LLMProvider 接缝多 profile（快路径小模型、agentic 大模型）；召回/排序作为非 LLM 服务挂在接缝后；多级缓存进一步跳过这些调用
5 扩展模型 一切皆插件、热插拔、可逆 effect、运行时自改 少量固定 seam + 配置选择 DSH 的插件机制为开放工具空间与运行期组合付出成本；搜推的组件空间封闭、变更发生在部署期。高 QPS 下运行时热插拔仅增加风险（负载中加载缺陷插件）而无收益 借 seam（Definition/Provider/Consumer）与 Bundle/Profile/Patch 的配置分层，弃微内核与热插拔；换实现 = 部署期改配置
6 失败模式 / guard 权限 waterfall，拦截不可逆动作 预算 / 质量 gate；操作只读、无不可逆动作 风险面不同：通用 harness 防护文件系统与外部世界的不可逆操作；搜推 harness 防护 SLA 与推理成本 以 budget-waterfall 替代 permission-waterfall（时延/token/轮次/成本上限 + 降级阶梯），并以 Trace 支撑质量监控（误判率、排序指标）
7 并发模型 单进程单线程协程 水平无状态副本 人工交互量级下单事件循环足够；万级 QPS 下不足 快路径无状态副本 + LB；状态外置 Redis；唯一有状态的 agentic checkpointer 也外置，任意副本可续

借鉴与舍弃清单：

  • 借：Capability Seam（稳定契约 + 可换实现）、双轨 / 事件溯源（但仅异步、仅用于训练与观测）、Bundle/Profile/Patch 的配置分层、waterfall 作为”预算拦截链”。
  • 弃：微内核与热插拔、热路径上的模型驱动循环、进程内 append-only session log、单进程并发模型。

13.2 落地：两层 + 一套接缝

四项设计决定：

  1. Agentic 走 SSE 流式 + 硬上限（轮次/时延/token），达到上限时不报错而是降级，返回当前最优的部分结果并提供”继续”入口。
  2. 模型自托管 vLLM/SGLang，隔一层 OpenAI 兼容的 LLMProvider 接缝，后端可换。
  3. 两层都用 LangGraph（技术栈一致），但快路径启动时编译一次、不挂 checkpointer（无状态、可水平扩、热路径不付 checkpoint I/O）；agentic 挂 Redis 后端 checkpointer 做多步可恢复。同框架、两套 config。
  4. 缓存中间产物：L1 结果 / L2 召回集 / L3 排序 + 向量库（Milvus/Qdrant）。依据是”召回与排序对 (query, 目录版本) 是纯函数”，因此 L1 未命中时仍可命中 L2/L3，仅需重做成本最低的合成步骤。

开源无锁定：Redis 协议（Valkey/KeyDB 等兼容实现均可）、OpenAI 兼容端点、OTel、Milvus/Qdrant、Kafka、FastAPI/Ray Serve；配置采用版本化 YAML/etcd，不依赖厂商专有 API。

13.3 维护成本分析

  • 一套接缝、两个调用方：修改 LLM/缓存/Trace 接缝一次，两层同时受益——seam 的复用收益。
  • 快路径是固定 DAG：易于推理、测试与快照；唯一含循环的是 agentic 层，即唯一需要重 guardrail 的位置，影响范围被限制在该层。
  • 阈值 / TTL 置于配置而非代码：调整分流与缓存参数无需发布。
  • Trace 同时产出训练与评估数据：后续改进 Router 分类器或小模型属于数据问题而非代码问题。

13.4 上线前需校准的不变式

  1. Router 误判：复杂 query 被错分至快路径会在无告警的情况下返回低质量结果。需引入低成本置信度、兜底策略与误判率监控，并以 Trace 回放校准 95/5 的分流假设。
  2. 中间缓存失效：召回/排序依赖目录版本，cache key 必须携带版本号，否则将返回过期数据——这是多级缓存的典型失效模式。
  3. Redis 职责分离：Surface 与缓存逻辑上分 DB / 分集群，避免缓存淘汰策略误删会话态。
  4. “快路径无环、无 checkpointer”不变式：以 config 约束加一条单测断言（图无环、无 checkpointer）保证，防止其演变为 agentic 循环而超出时延预算。

要点速查卡

  • 微内核：内核 = 解析 / 注册 / IPC / 生命周期，其余皆插件，无特权核心。
  • 插件 = 镜像，Fiber = 进程，注册 = 可逆 effect（逆序释放），事件 = IPC。
  • waterfall = 拦截器链：next() 委托，不调用即否决。
  • Session Log = 唯一事实源（event sourcing）；Surface / Transcript / Projection = 派生读模型；压缩只改 Surface。
  • Bus 瞬时、Log 持久、Surface 是投影——三者属于不同层次，不应混淆。
  • Seam = Definition（定标准）+ Provider（可换）+ Consumer（inject key）；内核按 scope 解析，policy 由 waterfall 插入。
  • ctx = 被 Proxy 包装的服务容器：读 ctx.xxx 是即时解析（服务解析），字段由各插件 provide 与声明合并动态注入；同作用域重名即报错。它是 Service Locator + Proxy，不是普通对象。
  • 运行模型：单进程 + 单 JS 线程 + 协程并发（await 处交替）；真并行仅在模型请求 / 子进程；共享 JS 状态无需加锁；多会话修改同一文件用乐观锁（FsVersion → FS_STALE_VERSION）+ 作用域隔离，不加锁。
  • 对比：LangGraph = 状态快照，DSH = 事件溯源。
  • 搜推 harness：两层（Router → 快路径 / Agentic）+ 一套开源接缝；借 seam / 双轨 / 配置分层，弃微内核热插拔与热路径模型循环；快路径固定 DAG 无 checkpointer，Agentic SSE + 硬上限。
  • 局限：复杂度转移、非安全沙箱、契约依赖约定；本质是为”自进化”预付的成本。
