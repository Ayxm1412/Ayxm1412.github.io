从 DeepSeek Harness 看 AI Native 软件的长期维护

发表于 2026-10-21 分类于 技术 阅读次数：

最近，日常研发中的大部分实现已经交给了 Agent，也写了不少用完即弃的“日抛代码”。我尝试过 Spec 驱动开发，希望把需求和实现管得更清楚。但代码越积越多，遇到问题时，还是经常只能再向 Agent 求助。

相比亲手写的代码，这些产出少了一些掌控感。新需求来了，或者出了 Bug，又回到“描述愿望，等待结果”的循环。Agent 能把代码写出来，但怎样才能让它成为团队真正理解、能够持续维护的软件？

《AI Native 研发范式实践手册》也记录了类似的“消化障碍”：团队并行使用多个 Agent，产出变多了，沟通方案时却未必能讲清设计，还得重新问 Agent。[1] 个人产能提高，并不等于团队的理解、评审和接手能力同步提高。

正巧最近读了 DeepSeek Harness 的部分源码。它以 Cordis 插件组织模型请求、工具执行和会话记录，仓库还维护着开发约定、文档检查、回放测试和设计说明。这些不直接实现功能的文件，提供了一个观察软件长期维护的窗口。

下面从问题定义、架构、文档和验证几个方面展开，再讨论开发进一步提速后，工具和工程师的工作可能怎样变化。文章结合个人实践与源码观察，由 Agent 协助润色。

一、先说清楚问题，再让实现加速

这也是为什么 Grill me 有存在价值。

一个很普通的需求：“外部服务偶尔超时，给它加一下重试。”

熟悉业务的人会接着问：认证失败要重试吗？用户取消后还继续吗？服务端可能已经写成功，只是响应丢了，再调一次会怎样？这些条件在需求里可能一个字都没有，却决定了实现是否正确。

假设两个 Agent 分别在请求层和工具层增加重试，每层最多尝试三次，包含首次请求。两个修改都有测试，合并也没有文本冲突，但一次操作最多可能发出九次外部调用。

次数展开示意，并非并行执行；提前成功或取消会减少实际调用。

让 Agent 修复叠加重试很快。但如果已经重复扣款，核对账目、退款和解释事故，并不会因为补丁来得快而省掉。

先明确谁负责、允许做什么、失败后留下什么状态，比先规定创建几个类更重要。 Agent 可以帮助找遗漏、比较方案，但缺失的业务事实不能靠推理补出来，取舍的后果也需要团队承担。

二、好的架构，让局部问题可以局部理解

一个小需求要读懂半个仓库才能修改，对人意味着高认知负担，对 Agent 则意味着反复搜索、消耗上下文，仍可能漏掉远处的依赖。更大的上下文窗口，也不代表模型能无损理解其中所有关系。

人机友好的架构，首先应该让人回答：只理解当前模块和少量接口，能不能安全完成这次修改？

新能力有去处，默认行为有归属

DeepSeek Harness 的架构文档明确列出扩展位置：模型提供者、工具、文件访问和持久化状态，分别通过对应服务、注册表或事件接入。功能留在所属插件，主流程负责通用编排，减少每加一个功能就去中央控制器补分支的情况。

Shell 的公开接口则把参数解析与执行分开：调用者可以省略参数，resolve 负责补全默认值、应用限制，execute 只接收完整规格。

默认值不需要由工具层、任务层和进程层各猜一次。调整策略时去找解析步骤，排查执行时去找执行步骤，后来者有明确的定位入口。

这与 Parnas 的信息隐藏思想相通：模块隔离可能变化的设计决定，让其他部分不必跟着理解和修改。[2] 重点不在拆出多少文件，而在一次变化会牵动多少地方。

状态和资源也要有主人

缓存由谁更新、后台进程由谁关闭，如果没有明确归属，模块拆得再细也容易互相干扰。项目通过 ctx.effect() 将注册与撤销关联到生命周期，避免依赖远处某个函数“记得清理”。

Session 则提供共同的历史依据：模型可见输入需要能够从日志重建，请求构造通过记录和投影得到消息，恢复、分叉与回放不必各维护一套独立事实。

不必照搬事件溯源，但值得检查自己的系统：一份状态改变后，如果要手动同步数据库、缓存、页面和日志，是不是独立写入的位置太多了？

三、减少漂移，先减少重复维护

很多 Spec 和注释不仅描述行为，还复述类、方法和调用顺序。第一次生成时很完整，几轮重构后却变成另一份过期实现。新来的 Agent 面对文档与代码的矛盾，甚至可能把正确的新实现改回旧方案。

DeepSeek Harness 先给信息安排位置：AGENTS.md放日常约定和导航，README 说明如何使用，设计记录保留取舍，复盘记录事故。一次功能修改只更新受影响的部分，不必重写全部材料。

可以计算的事实，交给程序核对

配置目录生成器根据源码重新计算文档，与已提交内容比较；类型对应清单则指定文档中的声明来自哪里，连原始 JSDoc 一起核对。

这是 DRY 更值得借鉴的一面：减少同一份知识的独立维护来源。 生成结果里有重复没关系，几份内容各改各的才容易漂移。

比较的不是 en 与 zh 相等，而是各自内容是否匹配记录。英文说“超时后报错”，中文说“自动重试”，重新记录后仍可能通过结构检查。因此，哈希负责发现变化，评审仍要判断含义。

Spec 和注释，保留对下一次修改有用的内容

参考手册建议区分约束与假设。[1] 数据不能出域、旧接口必须兼容，是需要保持的要求；缓存策略和实现方式，则应允许根据反馈调整。Spec 可以固定行为与验收条件，不必把每个私有方法都写成长期承诺。

注释也是如此。下面两句话的价值不同：

实现过程：遍历任务数组，收集停止 Promise，最后调用 Promise.all。

行为要求：销毁完成前，必须停止并等待本实例启动的任务结束。

前一句重构后就可能失效，后一句却帮助维护者判断重构是否正确。项目的 prose 标准因此保留失败、时机和所有权，删除对控制流程的复述。

注释的价值不在长短，而在它是否改变了读者的判断。 非零退出码是返回结果还是抛异常，必须说明；“本轮方案第几项”“上次 Review 要求”，则不该依赖已经离开的聊天上下文。

四、验收必须经过用户真正的入口

项目的一份复盘记录过：负责编辑器通信的 ACP 模块有 178 个通过的单元测试、100% 行覆盖率，但 Zed 一连接，创建对话就失败。

原因之一是多写了 export default apply。加载器优先取默认导出，只拿到执行函数，丢掉了模块中的依赖声明 inject。测试却手工组装了包含依赖的插件对象，绕过了这个加载过程。

示意复盘中的默认导出问题，不包含第二个故障。

后来补上的测试经过真实加载器，用实际协议创建 Session。创建会话不需要调用模型，因此无须 API Key；把错误导出加回去，新测试就会失败。

实现与测试彼此一致，不代表符合真实需求。 同一个 Agent 写出的两者可能共享误解，另一个 Agent 也可能沿用相同假设。独立的结果检查很重要：项目的 SDK 快照测试会比较实际工作区，刷新 Session 录制不会顺便重写这份预期。模型说“文件改好了”，不能替代文件真的改对。

验证还需要可运行的环境。我们在主要项目中，把实际请求参数和 SLS 日志提供给 Agent，本地开发后继续到预发环境批量回归，让它面对真实请求和运行反馈。数据需要脱敏，权限与副作用范围也要受控。

测试、环境和可观察的结果应当一起交付。否则下一位 Agent 还要重新猜依赖、补配置，之前省下的时间又花在同一轮排障里。

五、多个方案都能实现时，要有人判断代价

并行开发不能只按文件拆分，还要看任务是否共同改变了一个行为。重试由谁负责、共享状态怎样更新，应先约定清楚，再并行实现内部细节。独立 worktree 能隔离写入，不能替代组合版本的验证。

更难的问题是：几个方案都正确，选哪个？

DeepSeek Harness 曾为插件配置更新提供通用事务回滚，后来决定撤掉。自动恢复听起来更安全，但插件已经注册事件、建立连接、启动进程，要撤销这些副作用，还要管理依赖顺序和回滚本身的失败，加载器因此承担了过多责任。

项目转而让调用者检查激活、报告失败、完成清理，再通过后续正确编辑恢复。代价也明确：失败后，部分变更可能已经生效，不再保证自动回到旧状态。

支付和库存系统未必能接受这种取舍。值得学的是，一个能力已经实现，不等于值得永久维护。 设计记录要让后来者知道为什么放弃它，避免下一个 Agent 又把它当作遗漏补回来。项目也收缩过 Note 的创建要求：没有长期决策价值的局部修改，不必再制造一份文档。

六、当开发继续提速，工具和问题都会改变

这些实践并不是终点。今天觉得够用的版本管理、评审和验证方式，也可能跟不上明天的产出速度。

Anthropic 在 2026 年 10 月发布的文章中介绍，其日均合入变更从五月约 2,500 次增长到九月超过 30,000 次，并将内部单体仓库从 Git 迁移到自研 Scion。大量检出和同步已成为基础设施负担，Scion 把提交、合并和历史查询更多放到服务端处理。[5]

这不是“Git 已经过时”的普遍结论，而是提醒我们：工具的假设也有适用范围。当主要使用者变成持续在线、大量并行的 Agent 和 CI 任务，过去围绕个人工作副本组织的流程，可能需要重新设计。Anthropic 同时建设了审查工具 Antique，并投入合并后、部署前测试，并没有取消版本历史、评审与验证。

沿着这个方向，可能会有三种可能的变化。

评审可能从“读完所有差异”，转向“检查意图、影响和证据”。 一个变更除了代码，还应带上行为差异、依赖版本和验证结果。Reviewer 可以更快定位重要部分，但仍要追到关键实现，尤其不能让生成补丁的 Agent 同时随意改写验收标准。

开发环境可能从“一次性交接的工作区”，变成持续更新的项目状态。 假设一个 Agent 按昨天的接口开发，另一个今天刚改了接口，平台应能指出哪些测试和批准已过期，触发必要的重新验证。这比让双方再写几份摘要有效，也意味着工具需要理解的不只是文本冲突，还有行为依赖。

快速修复会获得更大空间，但必须配套限制影响的机制。 可隔离、可回退的小改动，可能更多依靠灰度和持续测试推进；涉及权限、账目与持久化数据，提前明确约束仍然重要。新的协作成本也会出现：大量 Agent 同时提交，可能挤占验证资源；各自修复局部问题，又可能反复推翻对方的修改。自动化放得越开，越需要明确谁对最终状态负责。

模型会进步，瓶颈也会迁移。未来的软件工程不仅要管理代码，还要管理并行行动、证据何时有效，以及错误能够影响多大范围。

七、程序员回归工程师，但工程师不能离开代码

Brooks 区分过软件的本质复杂性与实现过程中附带的困难。[3] 工具可以降低实现成本，却不会自动消除业务规则和状态之间的冲突。候选方案产生得越快，问题定义、架构设计和责任边界就越重要。

软件工程的 taste，在这里很具体：给重试确定唯一负责层，为真实调用者保留简单接口，留下等待退出的保证，而不是一整段私有方法说明。这些选择未必让演示更惊艳，却会让下一次修改少读几个文件、少猜几个条件。

“从建筑工人到设计师”可以形容工作重心的变化，但不能把设计和实现割裂。Jack Reeves 提出过，源代码本身就是软件设计。[4] 一个超时如何结束、事务在哪里提交，都要在代码里精确落定。

因此，工程师仍然需要读关键实现、调试和验证。初学者也需要通过复现故障、设计反例和小实验积累判断力，否则团队短期获得更多产出，长期却可能失去判断产出的人。

代码可以写得更快，但软件承载的现实关系不会因此变简单。最后，不妨用一个问题衡量我们的维护工作：

半年后，另一个人或 Agent 带着新需求进入仓库，能否知道该改哪里、哪些事情不能破坏，以及怎样确认自己没有改错？

如果答案越来越清楚，提速才真正留在了项目里。
