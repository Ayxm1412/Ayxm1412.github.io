Context-Centric Agent System：从操作系统设计哲学重新思考 Agent 架构

发表于 2026-10-22 分类于 技术 阅读次数：

这是我 4 月份的一份随笔，最近细读 deepseek harness 的代码的时候，发现想法不谋而合，也放在博客里吧。

CONTEXT-CENTRIC AGENT SYSTEM: RETHINKING AGENT ARCHITECTURE FROM OS DESIGN PHILOSOPHY

图 1：上为 Agent-Centric 的中心辐射结构，下为 Context-Centric 的分层流水线（Input → Router → ISA → CPU → Bus → I/O → Output → Evolve）。蓝框为可替换的处理器，虚线框为运行期能力。

当我们谈论 AI Agent 系统时，几乎所有的架构讨论都默认以 Agent 为中心——Agent 感知环境、做出推理、选择工具、获取反馈、再推理。这个被称为 Agent Loop 的模式，已经成为 LangChain、CrewAI、AutoGen 等主流框架的核心范式。

但如果我们退后一步，从操作系统设计的视角重新审视这个问题，会发现一个被忽视的根本性假设：为什么 Agent 必须在中心？

本文提出一种替代范式——Context-Centric Agent System（以 Context 为中心的 Agent 系统），并从操作系统的设计哲学出发，论证这种范式为何更符合未来 Agent 系统的演进方向。

一、Agent-Centric：现状与局限

当前主流的 Agent-Centric 架构本质上是一个主体决策循环（Subject Decision Loop）：

Agent 接收输入 → 推理 → 决定调用哪个工具 → 获取结果 → 再推理 → 输出

这个模式直觉上很自然，因为它模拟了人类的认知模型——有一个”我”在思考和行动。Agent 是系统的大脑和心脏，context、tool、memory 都是围绕它的从属组件。

这种设计在早期阶段是合理的。当 LLM 能力有限、场景简单时，一个”聪明的中心”足以协调一切。但随着系统复杂度的增长，它的结构性缺陷逐渐暴露：

Context 管理是真正的瓶颈。 在实际生产环境中，Agent 系统的失败原因大多不是”推理不够好”，而是 context 管理出了问题——关键信息丢失、无关信息堆积、上下文窗口溢出。Context 在 Agent-Centric 架构中只是一个”传入参数”，没有自己的生命周期管理。

模型替换代价极高。 整个系统的 prompt engineering、行为预期、错误处理都是围绕特定模型的特性构建的。更换模型（比如从 GPT-4 切到 Claude）往往需要大量的 prompt 重写和行为调优，因为系统与特定 Agent 的实现深度耦合。

Multi-Agent 协作困难。 当多个 Agent 需要协作时，Agent-Centric 架构的协作方式是”消息传递”——Agent 之间互相喊话。这种模式难以扩展，信息同步成本高，且缺乏结构化的协作机制。

单点失败风险。 Agent 是唯一的决策中心，一旦推理出错（hallucination、逻辑错误、工具选择失误），整个链路崩溃，没有自然的容错和重路由机制。

二、Context-Centric：一种替代范式

Context-Centric Agent System 的核心思想很简单：把 Context 放在系统的中心，把 Agent 降级为 Context 的处理器。

这个想法并非凭空而来。在经典 AI 中，有一个被称为 Blackboard Architecture（黑板架构） 的先驱范式（Nii, 1986）。在黑板架构中，有一个共享的中央数据结构（blackboard），多个 Knowledge Source 围绕它读写操作，而一个控制组件决定何时激活哪个 Knowledge Source。Blackboard 就是我们所说的 Context，Knowledge Source 就是 Agent。Context-Centric 可以看作是黑板架构在 LLM 时代的重新诠释——继承其”数据为中心”的哲学，但利用大语言模型作为通用处理器来替代传统的规则引擎。

在这种架构中，Context 不再是被动的传入参数，而是一个有结构、可版本化、可路由的一等实体（First-Class Entity）。它拥有自己的生命周期——被创建、被丰富、被压缩、被分发、被归档。而 Agent 简化为 Context 流水线上的一个处理环节：接收 context，执行转换，输出更新后的 context。

这种设计的关键转变在于：控制流从”Agent 决定做什么”变为”Context 的状态决定它流向哪里”。 一个轻量级的 Context Router 根据 context 的类型、状态、优先级，将其分发到合适的 Agent 处理。Agent 不需要理解全局任务，只需要忠实地完成自己负责的 context 转换。

用一个直观的对比：

Agent-Centric 像是一个全能项目经理，所有信息汇报给他，他做出所有决策，分配所有任务。这在小团队很高效，但在大组织中会成为瓶颈。

Context-Centric 像是一条装配流水线。工件（Context）沿着产线流动，每个工位（Agent）完成自己的工序。流水线的效率取决于工件的路由和调度，而不是某一个工位有多聪明。

三、计算机架构的类比

这种范式转换，在计算机架构的演进中有一个精确的类比。

Context 是文件系统（File System）。 它是系统需要处理的”工作负载”。文件有格式、有元数据、有存储位置、有访问权限、有版本历史。同样，Context 也应该有结构定义（schema）、有元信息（来源、优先级、过期时间）、有版本控制、有访问控制。

Agent 是 CPU。 它是通用的处理单元，与具体任务无关。CPU 不关心自己处理的是数据库查询还是视频渲染，Agent 也不应该关心自己处理的是客服对话还是代码审查——它只需要实现标准化的处理接口。更关键的是，CPU 的升级对上层软件是透明的。你把 Intel 第 12 代换成第 14 代，操作系统和应用不需要任何修改。Agent 的替换也应该如此——换一个更强的模型，系统层面的代码一行不改。

但这个类比需要一个重要的限定：CPU 是确定性的，LLM 是概率性的。 同一条 x86 指令在任何兼容 CPU 上的执行结果完全一致；但同一个 Skill 调用在不同 LLM 上的输出可能有显著差异——不仅是质量差异，甚至是行为模式的差异。这意味着 Agent 的”可替换性”不会像换 CPU 那样无缝，更接近于同一 ISA 下不同微架构的差异：接口兼容但性能特征不同，某些边界场景下行为可能不一致。系统设计时必须为这种”概率性兼容”留出容错空间，比如输出校验、行为回归测试、质量基线门槛。

Skill 是指令集架构（ISA, Instruction Set Architecture）。 ISA 是 CPU 与软件之间的契约层：向上对软件承诺”你可以用这些操作”，向下对硬件说”你必须实现这些操作”。Skill 在 Context-Centric 系统中扮演类似的角色——定义标准化的能力接口（summarize、generate、analyze、extract），不管底层是哪个模型，只要它实现了这套 Skill 接口，就可以接入系统。

但这里有一个本质差异必须诚实面对：ISA 是精确的二进制契约，Skill 是模糊的能力承诺。 ADD EAX, EBX 的语义在任何 x86 CPU 上毫无歧义；但 Skill:Summarize 的输出质量、风格、甚至对”摘要”的理解，在不同模型间差异巨大。这意味着 Skill 层的”契约”更接近于 API 的语义版本控制（Semantic Versioning）而非硬件 ISA 的位级精确——它需要包含质量基线定义、输入输出 schema 约束、以及行为测试套件来保证兼容性。Skill 的标准化是这套架构能否落地的关键技术瓶颈。

ISA 的演进方式仍然适用于 Skill 的能力扩展：x86 从基础指令集逐步扩展出 SSE、AVX 等扩展指令集来处理新场景；Skill 同样可以从基础能力（文本理解、生成）逐步扩展领域 Skill（PDF 处理、代码审查、数据分析），形成可扩展的能力分层。

Tool 是 I/O 设备。 搜索引擎、数据库、API——这些不是 Agent 的内在能力，而是通过标准总线协议（Tool Schema）访问的外部资源。操作系统通过设备驱动（Tool Adapter）让 CPU 统一访问各种外设，Context-Centric 系统也应该通过统一的 Tool 接口层让 Agent 访问外部服务。

Context Window 管理是虚拟内存（Virtual Memory）。 当前大多数 Agent 系统对 context window 的管理，相当于早期计算机没有虚拟内存的状态——所有东西直接加载到物理内存，满了就崩。成熟的做法应该像虚拟内存一样：context 按需分页加载（page in），不活跃的 context 换出到外部存储（page out）。虚拟内存最关键的特性是对进程透明——进程不知道自己的哪些页面在物理内存、哪些在磁盘上。现在的 RAG 本质上是一种”检索式加载”机制，但它不具备虚拟内存的透明性——Agent 通常能感知到 RAG 的存在（需要主动触发检索查询），这更接近于早期的覆盖技术（overlay）而非真正的虚拟内存。一个真正的 context 虚拟化层应该让 Agent 像访问”无限 context window”一样工作，所有的分页调度对 Agent 完全不可见。

Context 亲近度是缓存层级（Cache Hierarchy）。 L1 Cache 是当前 prompt 中的内容，访问延迟最低但容量最小；L2 Cache 是同一 session 的历史对话；L3 Cache 是持久化的知识库；Disk 是外部数据源。好的系统应该有一个 Context Cache Hierarchy，自动管理什么信息放在哪一层、什么时候预取、什么时候淘汰。值得注意的是，CPU 缓存系统中最棘手的问题之一是缓存一致性（cache coherence）——当多个核心缓存了同一数据的不同副本时，如何保证一致？Context Cache Hierarchy 同样面临这个问题：当 L3（知识库）更新了，但 L2（会话历史）仍引用旧版本信息时，系统需要一个一致性协议来检测和处理冲突。这个问题在当前讨论中被低估了。

Context Router 是进程调度器（Process Scheduler）。 操作系统的调度器是一个轻量、明确的组件——它不是另一个应用程序，只做一件事：决定哪个进程下一个上 CPU。Context Router 也应该如此：一个薄层，根据 context 的类型和状态，决定它该被哪个 Agent 处理。

Context Pipe 是 Unix 管道（Pipe）。 Unix 的哲学是”每个程序做好一件事，通过管道组合”。cat file | grep pattern | sort | uniq——每个命令是一个专注的文本处理器，通过标准化的 stdin/stdout 接口串联。Context-Centric 系统也应该这样：每个 Agent 是一个专注的 Context Transformer，通过标准化的 Context 接口串联，实现管道式组合。

四、Context Bus：让非语义数据绕过 Agent

在搜索推荐（Search & Recommendation）等场景中，有一个长期困扰工程师的问题：召回阶段和排序阶段之间需要传递 itemID、session token、tracking code 等数据。这些数据对流水线的路由和追踪至关重要，但对 LLM 的逻辑推理来说完全无意义——它们是任意编码的标识符，不携带任何语义信息。

如果把这些 ID 塞进 prompt，强迫 Agent “处理”它们，结果是灾难性的。LLM 会尝试对这些无意义的 token 进行”推理”，导致严重的幻觉：输出的 itemID 可能是编造的、截断的、或者与输入不匹配的。这不是模型的”能力不足”，而是架构设计的错误——你让 CPU 做了 DMA 控制器该做的事。

在操作系统中，DMA（Direct Memory Access） 解决的正是这类问题：大量数据需要在外设和内存之间搬运，但 CPU 不需要理解这些数据的内容。DMA 控制器让数据绕过 CPU 直接传输，CPU 只在传输完成后收到一个中断通知。

Context-Centric 系统应该有一个对等的机制——Context Bus。它的核心设计是将 context 中的数据分为两类：

语义数据（Semantic Payload） 需要 Agent 理解和推理的内容——用户意图、文本描述、业务逻辑。这部分进入 Agent 的处理管道。

引用数据（Reference / Pointer） 不需要 Agent 理解，只需要在流水线各阶段之间精确传递的数据——itemID、文档哈希、会话标识、坐标索引。这部分通过 Context Bus 旁路传输，Agent 只拿到一个轻量级的引用（类似文件描述符 file descriptor），而不是原始数据。

当 Agent 的推理结果需要关联到具体 item 时，它输出的是语义层面的描述（比如”排名前 3 的结果”），Context Bus 负责将这个语义描述解析为对应的 itemID 引用。这样，Agent 永远不需要”记住”或”复述”那些任意编码的 ID，幻觉问题从架构层面被消除。

这个模式的适用范围远不止搜推场景。任何涉及”对 Agent 推理无意义但对系统流转必要”的数据——数据库主键、API token、二进制文件句柄、地理坐标编码——都应该走 Context Bus 而不是 Agent 的推理通道。这是一个通用的架构原则：分离语义通道和数据通道，就像计算机分离控制总线和数据总线一样。

五、Self-Improving：当执行产出变成新的指令

Context-Centric 架构的另一个深远优势是它对 self-improving（自我改进） 天然友好。

在 Agent-Centric 系统中，self-improving 是一个棘手的悖论。你要改进的对象——Agent——恰好是系统的控制中心。这就像要求一台正在运行的计算机在不停机的情况下更换自己的 CPU。你可以在 Agent 的 prompt 里加入”反思”环节，但这本质上只是在同一个推理循环里增加了一步，并没有真正扩展系统的能力边界。

在 Context-Centric 系统中，self-improving 的逻辑截然不同，因为 Skill（ISA）和 Agent（CPU）是解耦的。一次 Agent 执行的输出不仅仅是任务结果，它可以是一个新的 Context，而这个 Context 的内容恰好是一条新的 Skill 定义或一条优化后的 Instruction。

这意味着系统的能力扩展路径变成了：执行 → 产出新 context → 新 context 被识别为 skill 定义 → ISA 自然扩展 → 下一次执行使用增强后的 ISA。

这个过程在操作系统中也有对应的类比，但需要注意差异。用户安装软件是一个有意为之的人工动作——用户选择安装什么、确认安装、可以卸载。而 self-improving 的 skill 生成是自动发生的。更准确的类比可能是包管理器的自动更新加上依赖解析——系统观察到需求后自动安装新能力，但这同时引入了一个 OS 早就解决过的问题：自动安装的软件需要签名验证、沙箱测试、回滚机制。自动生成的 Skill 也需要类似的质量门控——不经验证就加入 ISA 的 Skill 可能引入”能力退化”，就像未经测试的软件更新可能导致系统不稳定。

这个类比还可以进一步延伸到 JIT（Just-In-Time）编译。JIT 编译器在运行时观察程序的执行模式，动态生成优化后的机器码。Context-Centric 系统也可以有类似的机制：观察某类 context 的反复处理模式，自动生成一条新的 Skill 来加速后续处理。系统在使用中自我进化，而这个进化过程完全发生在 Context 层面，Agent 保持不变。

六、实证检验：Claude Code、OpenClaw 与 Hermes 的启示

上述分析如果只是纸上推演，说服力有限。我们需要用真实系统来检验：当前最前沿的 agent 系统，到底在 OS 成熟度光谱上走到了哪里？以下基于 Claude Code、OpenClaw 和 Hermes Agent 三个代表性系统的架构分析。

内存隔离和安全模型——比预期成熟。 Claude Code 的子 agent 有独立的 context window，支持 isolation: worktree 在独立的 git 工作目录中运行，执行结果只以摘要形式返回——这相当于进程间通过消息传递而非共享内存通信。它的权限系统已接近 OS 级别的能力模型：四级配置（Managed → User → Project → Local），支持精确到 Bash(git diff *) 粒度的 allow/ask/deny 规则，甚至有 OS 级沙箱（macOS Seatbelt / Linux bubblewrap）。OpenClaw 更彻底——agent 之间”完全隔离”，跨 agent 通信需显式启用白名单，有三级 kill switch（撤销 JWT → 零速率限制 → 缩容 gateway 到零）。

进程管理——有进展但远未成熟。 OpenClaw 有两层 FIFO 队列（session 序列化 + 全局并发控制 maxConcurrent=4），并且它的 steer 模式可以在运行中注入方向指令。Claude Code 用 git worktree 实现了并行子 agent 的物理隔离。但和 OS 相比，没有系统有优先级调度、时间片轮转或真正的任务挂起/恢复。

中断机制——仍是最大空白。 三个系统都没有真正的异步中断。OpenClaw 的 steer 只能在 tool call 间隙注入，不能打断推理过程。Hermes 每 15 次 tool call 的自评估检查点是内部轮询而非外部中断。Claude Code 只有手动 /stop。用户无法在 agent 走错路时实时纠偏——只能等待或终止。

持久化与 Self-Improving——Hermes 是先行者。 Hermes 的三层记忆（session / persistent / user model）加 FTS5 全文搜索索引是三个系统中最结构化的。它的 closed learning loop（执行 → 自评估 → 创建 skill → 更新记忆）直接验证了我们”执行产出变成新 ISA 指令”的论点——skill 以 Markdown 文件存储在 ~/.hermes/skills/，遵循 agentskills.io 标准。经过 20-30 个复杂任务后，同类任务的 tool call 从 25 次降到 8-10 次。但随着 skill 库增长 token 消耗增加，Hermes 用”progressive disclosure”（先加载摘要再按需展开）来解决——这本质上就是我们说的 context cache hierarchy。

IPC 和可观测性——仍然原始。 OpenClaw 的 coordinator-specialist 模式和中心 gateway 是最接近结构化 IPC 的设计，但通信仍是非结构化文本，缺少消息确认、背压、优先级。三个系统都有日志和 hook 机制，但这些是面向开发者的调试工具，不是面向终端用户的可观测性界面。

需要谨慎解读的趋势：三个系统都在加强 Context 管理能力，但这不等于它们在走向 Context-Centric。 Claude Code 最重视的不是推理能力，而是 context 工程（CLAUDE.md 三层记忆、compaction 策略、context isolation）。OpenClaw 的核心创新是 gateway 总线和 routing bindings——本质上是 context 的路由和调度。Hermes 的核心创新是 skill learning loop——把执行结果转化为可复用的 context。这些实践表明 context 管理的重要性正在被行业广泛认知，但把它解读为”向 Context-Centric 架构范式的不自觉滑动”可能存在确认偏误。更审慎的说法是：这些系统在 Agent-Centric 框架内大幅提升了 context 管理的优先级和成熟度，这验证了 context 管理是核心瓶颈的判断，但不直接证明 Context-Centric 作为替代架构的优越性。 从 “context 很重要” 到 “context 应该成为架构中心” 之间，仍有一段需要论证的距离。

七、面向用户的第一性原理分析

如果我们抛开所有架构术语，回到最基本的问题——用户到底需要什么？——那么 agent 系统的缺陷优先级会和从纯工程角度看非常不同。

从用户视角出发，只有四个核心诉求：任务完成（agent 把我要的事做完、做对）、可控性（我能在过程中干预、纠偏、中止）、可信赖（它不会做超出授权的事，做错了能回滚）、持续进步（它会越用越好，记住我的偏好和经验）。

这里需要诚实地承认一个张力：用户的第一诉求是”任务完成”，而任务完成在当前阶段仍然主要依赖 Agent 的推理质量，而非 context 管理。 一个推理能力强但 context 管理粗糙的系统，往往比一个推理能力弱但 context 管理精良的系统更能完成用户任务。Context-Centric 架构的论点不是”context 管理比推理能力更重要”，而是”当推理能力成为标准化商品后，context 管理将成为差异化因素”——这是一个对未来的判断，不是对当下的描述。在当前的过渡阶段，context 管理和推理能力同等重要，不应厚此薄彼。

用这四个诉求去审视 OS 级别的缺陷，优先级排序会变成这样：

P0：Context 失忆与丢失。 这是用户感知最强烈的痛点——“我刚刚说过的话它怎么忘了？””为什么同样的错误它反复犯？”几乎所有长任务失败都可以追溯到 context 管理的问题。对应 OS 中的虚拟内存管理——当前系统相当于没有虚拟内存的早期计算机，物理内存（context window）满了就崩溃。三个系统都在用 compaction/compact 机制兜底（相当于手动释放内存），但没有系统实现了透明的按需分页。

P0：不可中断、不可纠偏。 这是用户体验中最令人沮丧的问题——看着 agent 一步步走向错误的方向，却无法打断。对应 OS 中的中断机制。这不仅是技术问题，更是信任问题：如果我不能在需要时拉住缰绳，我就不敢让 agent 做重要的事。三个系统在这方面几乎都是空白。

P1：黑盒操作与信任缺失。 “它在干什么？为什么选了这个工具而不是那个？执行到哪一步了？”对应 OS 中的可观测性（strace、/proc、top）。当前系统有面向开发者的日志和 hook，但缺少面向终端用户的实时执行可视化和决策解释。

P1：操作不可逆。 agent 执行了一个错误的命令（比如删了不该删的文件），用户发现没有”undo”。对应 OS 中的事务和日志文件系统。Claude Code 有 checkpoint 机制但不追踪 Bash 操作——这恰恰是最危险的缺口。

除了上述从 OS 类比中识别出的缺陷，从用户视角还能发现两个 OS 类比中不易看到的新缺陷：

新缺陷一：无资源计量与预算机制。 OS 有 cgroups、ulimit、nice 值来控制进程的资源消耗。但当前 agent 系统中，用户不知道一个任务会消耗多少 token、花费多少钱，无法为任务设定预算上限。对于面向用户的应用来说，”用了多少钱”可能比”用了多少算力”更直接。这是一个 OS 中存在但在 agent 系统中被完全忽视的能力——你能想象一个操作系统不告诉你每个进程用了多少 CPU 和内存吗？

新缺陷二：缺少语义层面的保护环。 OS 有 Ring 0（内核态）和 Ring 3（用户态）的隔离——用户程序无论怎么写都不能直接操作硬件或修改内核内存。当前 agent 系统有文件系统级别的沙箱（Claude Code 的 Seatbelt、OpenClaw 的 sandbox mode），但缺少语义层面的保护环——一句错误的 prompt（”删除所有测试文件”本意是删除测试用例但 agent 理解为删除所有文件）可以穿透所有防线。需要的不是更多的 allow/deny 规则，而是一个语义理解层——agent 在执行高风险操作前，用一个独立的”内核态”验证机制来确认操作的语义是否符合用户意图，就像 OS 内核在切换到特权模式前的权限检查。

从第一性原理看，当前 agent 系统最大的问题不是它们不够”聪明”，而是它们不够”可控”。用户对 agent 的信任度低，根源不是推理能力不足，而是缺少控制面——不能中断、不能回滚、不知道发生了什么、不知道要花多少钱。操作系统用了几十年的时间告诉我们：一个系统从”能用”到”可信赖”的关键不是处理器更快，而是控制面更完善。Agent 系统需要补的，正是这一课。

八、从 OS 设计哲学看未来方向

如果我们从操作系统几十年的演进历史中提取设计哲学，可以得到几个判断 Agent 架构未来走向的关键原则。

原则一：硬件标准化之后，软件和数据管理才是竞争力。

计算机发展的早期，程序员直接操作硬件，手动管理内存，因为机器太贵太稀缺，必须榨干每一条指令的性能。但随着硬件标准化和摩尔定律的推进，竞争力从”怎么用好这块 CPU”转向了”怎么管理文件系统、怎么设计操作系统、怎么构建数据库”。

AI Agent 系统正处在类似的阶段转换中。当前我们还在”英雄时代”——LLM 能力有限、成本高昂，所有精力都放在”怎么让 Agent 更聪明”上（精心设计 prompt、微调行为、手动编排工具调用）。但 LLM 正在快速标准化和商品化。当推理能力不再稀缺时，”怎么管理 Context”将成为真正的差异化因素。

原则二：好的抽象层会催生生态。

ISA 的出现让硬件和软件各自独立演进——硬件厂商可以自由优化微架构，软件开发者不用关心底层实现。这个抽象层催生了整个计算机产业的生态繁荣。

在 Agent 系统中，Skill 接口如果能成为类似 ISA 的标准抽象层，将带来同样的解耦效应：模型提供商专注于提升基础能力（造更快的 CPU），Skill 开发者专注于定义领域能力（编写标准库），应用开发者专注于编排 Context 流（写应用程序）。当前这三者是高度耦合的，一个 prompt 里混杂着模型调优、能力定义和业务逻辑。

原则三：控制流应该从数据的结构中涌现，而不是由中心节点命令。

这是 Unix 哲学的核心——数据通过管道流动，每个程序只处理自己那一段，整个系统的行为从管道的组合中涌现。这比一个中心调度器指挥一切要健壮得多，也灵活得多。

Agent-Centric 架构的控制流是命令式的（imperative）：Agent 说”先做 A，再做 B，如果失败做 C”。Context-Centric 架构的控制流是声明式的（declarative）：Context 的状态本身决定了它该走向哪里，系统的行为从 Context 的流转规则中涌现。这种声明式的控制模型天然具有更好的容错性、可组合性和可观测性。

原则四：状态管理的集中化是复杂系统的必然趋势。

早期的程序把数据散落在各处——寄存器、内存、磁带。后来，文件系统把数据集中管理，数据库更进一步提供了结构化查询和事务保证。这个趋势的驱动力是：当系统变得复杂时，散落的状态会变成不可管理的噩梦。

当前 Agent-Centric 系统的状态散落在 Agent 的推理链、对话历史、工具返回值中，没有统一的状态视图。Context-Centric 架构将所有状态集中在 Context Object 中，提供了类似数据库的”单一事实来源”（Single Source of Truth），使得状态的查询、回溯、分支、合并都成为可能。

九、Context-Centric 的挑战与开放问题

诚实地说，Context-Centric 并不是一个无代价的选择。它面临几个需要解决的关键挑战：

路由决策的智能性。 Context Router 需要”理解” context 才能做出好的路由决策，但我们又不希望它变成另一个重量级 Agent。如何在轻量和智能之间找到平衡？这可能需要一种”分级路由”机制——简单的 context 用规则路由，复杂的 context 用轻量模型路由。

Context Schema 的设计。 统一的 Context 结构是这套架构的基础，但不同领域的 context 差异巨大。如何设计一个既通用又不过度抽象的 Context Schema？这需要在实践中迭代。

生态冷启动。 类比 ISA——x86 之所以成功不只因为设计好，更因为生态网络效应。Skill 接口的标准化需要行业共识，这是一个典型的鸡生蛋问题。

当前 LLM 的限制。 现有的 LLM 是为对话式交互设计的，它们天然适合 Agent-Centric 模式。让它们作为无状态的 Context Processor 工作，可能需要不同的调用模式和微调策略。

Pipeline 模型的适用边界。 Context-Centric 的”流水线”隐喻对结构化、可预测的任务（数据处理、文档生成、代码审查）非常自然，但对开放式、创造性的任务（头脑风暴、复杂推理、策略规划）并不天然适配。这类任务的本质是探索性的——它们的 context 路由无法在任务开始时确定，需要在推理过程中动态涌现。一个纯粹的 pipeline 模型可能会过度结构化这些任务，反而损害 Agent 的创造性推理能力。系统可能需要同时支持 pipeline 模式和 free-form 模式，根据任务特征自动切换。

确定性架构 vs 概率性执行的根本张力。 操作系统的所有抽象（ISA、虚拟内存、进程调度）都建立在底层硬件的确定性行为之上。但 LLM 本质上是概率性的——同一输入可能产生不同输出。这意味着从 OS 借鉴的架构模式在迁移到 Agent 系统时，可能需要根本性的适配。例如：虚拟内存的页面替换策略可以基于精确的访问频率统计，但 context 的”重要性”评估本身就需要语义理解。OS 的确定性假设是这套类比框架的结构性局限，本文的所有 OS 类比都应在这个前提下理解。

十、结论：从 Agent Engineering 到 Context Engineering

Agent-Centric 和 Context-Centric 不是非此即彼的二元选择。更可能的演进路径是：短期内 Agent-Centric 继续主导（因为当前 LLM 的能力边界要求精心的 Agent 设计），但中长期会向 Context-Centric 迁移（因为模型能力的标准化会让 Agent 变成可替换的通用处理器）。

这和计算机的演进完全一致：在机器稀缺的年代，程序员直接面向硬件编程；硬件标准化之后，操作系统和数据管理才是真正的战场。

如果说当前的 AI 工程主流是 Prompt Engineering（让 Agent 更聪明），那么下一个阶段的重心将向 Context Engineering（让 Context 的管理更优秀）倾斜。但这不是一个替代关系——Prompt Engineering 不会消失，就像汇编语言优化在有了编译器之后仍然在关键路径上不可替代。更准确的说法是：系统级竞争力的重心将从 Agent 优化转向 Context 管理，但 Agent 的推理质量始终是地基，Context 管理是在地基之上构建的上层建筑。这不仅是架构风格的转变，更是一次认知框架的升级——从”以主体为中心”到”以信息为中心”，从”命令式控制”到”声明式涌现”。

“当 CPU 足够快、足够便宜、足够标准化之后，没人再讨论怎么优化 CPU——大家讨论的是怎么设计文件系统、怎么构建数据库。AI Agent 的未来也是如此。”
